# CHAPTER 4: EXECUTION AND DEPLOYMENT DETAILS

The full operational runbook, including a troubleshooting table, is in the
repository at `docs/deployment.md`. This chapter covers the environments and the
procedures.

## 4.1 Execution Environment

**Development**

| Component | Setup |
|---|---|
| Backend | Python 3.11-slim container, port 8000 |
| Database | `pgvector/pgvector:pg15`, port 5432 |
| Search | `searxng/searxng:latest`, port 8080 |
| Frontend | Vite dev server, Node 18+, port 5173 |
| LLM | Groq API, `openai/gpt-oss-20b` |
| Embeddings | `all-MiniLM-L6-v2`, running locally on CPU |

Three containers under one `docker-compose.yaml`. The frontend runs on the host
rather than in a container so hot reload stays fast.

**Production**

| Component | Setup |
|---|---|
| Backend | Render web service, Docker runtime, free plan |
| Database | Render PostgreSQL 15, free plan |
| Frontend | Vercel static hosting |
| Config | `render.yaml` and `frontend/vercel.json` |
| Secrets | Managed by the platform, `JWT_SECRET` generated by Render |

The development image is about 2 GB because it includes PyTorch. The production
image is around 400 MB.

## 4.2 Local Deployment

```bash
git clone https://github.com/its-wasp/personal-adaptive-tutor.git
cd personal-adaptive-tutor
cp .env.example .env
# set GROQ_API_KEY and JWT_SECRET in .env

docker compose up
```

On first boot the entrypoint prints `[entrypoint]` lines as it waits for
Postgres, runs `alembic upgrade head` and seeds the knowledge graph. Compose's
`depends_on` only waits for the container to exist, not for the database to
accept connections, which is why the wait loop is there. Both steps are
idempotent so later starts skip them.

This automation was added during the hardening phase. Before it, the migration
and seeding steps were undocumented and a fresh clone gave you a running API on
an empty database with a blank dashboard. That was defect D7.

Then start the frontend:

```bash
cd frontend
npm install
npm run dev
```

Verify with:

```bash
curl http://localhost:8000/health        # {"status":"ok"}
curl http://localhost:8000/health/db     # {"status":"ok","database":"connected"}
python backend/scripts/smoke_test.py     # full end-to-end suite
```

Optionally seed reference content for RAG. The tutor works without it but
grounding is noticeably better with it:

```bash
docker compose exec backend python -m app.rag.content_seeder
```

That takes about ten minutes for all 25 concepts, pacing itself to stay inside
Groq's rate limit.

## 4.3 Cloud Deployment

### 4.3.1 Order of operations

The two halves depend on each other. The frontend build needs the API URL, and
the API's CORS list needs the frontend URL. Neither exists at the start, so:

1. Deploy the backend on Render, get the API URL
2. Deploy the frontend on Vercel with `VITE_API_URL` set, get the site URL
3. Set `CORS_ORIGINS` on Render to that site URL and redeploy

Skipping step 3 gives you a site that loads fine and then fails every request at
the CORS preflight, which looks like a broken frontend even though the backend
is healthy.

### 4.3.2 Backend and database

Render reads `render.yaml` as a Blueprint and creates both the web service and
the Postgres instance. `DATABASE_URL` is wired from the database automatically
and `JWT_SECRET` is generated by Render, so neither is ever committed. Two
values are marked `sync: false` so Render asks for them on first apply:
`GROQ_API_KEY`, which is a secret, and `CORS_ORIGINS`, which is not known yet.

The health check path is `/health`, which does not touch the database. A failed
migration therefore shows up as an unhealthy deploy rather than a service that
starts and then errors on every request.

### 4.3.3 Frontend

Imported into Vercel with the root directory set to `frontend`, which is
required for `vercel.json` to be picked up. `VITE_API_URL` is set to the Render
URL. Vite inlines that at build time, so changing it later needs a new deploy.

The important part of that config is the SPA rewrite. React Router owns
`/chat/:sessionId`, `/review` and `/profile` entirely on the client, so a hard
refresh or a shared link asks the host for a path with no file behind it.
Everything that is not a built asset is rewritten to `index.html`. We excluded
`/assets/` so a genuinely missing bundle still returns a 404 rather than HTML.

### 4.3.4 Configuration

| Variable | Required | Notes |
|---|---|---|
| `GROQ_API_KEY` | Yes | Chat and quiz generation fail without it |
| `JWT_SECRET` | Yes | Generated by Render in production |
| `DATABASE_URL` | Cloud | Takes precedence over the `POSTGRES_*` set |
| `CORS_ORIGINS` | Cloud | Comma-separated, localhost always allowed |
| `AUTO_MIGRATE` | No | Default 1, set 0 to skip migrate and seed |
| `SEARXNG_URL` | No | Empty disables `/references` |
| `VITE_API_URL` | Yes | Build-time, redeploy after changing |

## 4.4 Differences Between Environments

Three differences are deliberate.

**RAG is off in production.** The deployed image installs
`requirements-prod.txt`, which leaves out sentence-transformers because with
PyTorch the image goes past 2 GB and the free tier rejects it. The embedder
notices the missing import, disables itself, and the retriever returns nothing.
The tutor still personalizes from the profile, mastery and conversation history.
Nothing errors. The dependency set is chosen by a Docker build argument, so
turning RAG back on with paid hosting is a one-flag change.

**SearXNG is not deployed.** Running a meta-search engine next to a free web
service is not practical. Only `/references` is affected and no screen uses it.

**Cold starts.** Render idles a free service, so the first request after a quiet
period takes 30 to 60 seconds. Worth warming up `/health` before a demo.
