# CHAPTER 4: EXECUTION AND DEPLOYMENT DETAILS

The operational runbook, including a troubleshooting table, is maintained in
the repository at `docs/deployment.md`. This chapter records the environments,
the procedures and the differences between them.

## 4.1 Execution Environment

### 4.1.1 Development

| Component | Specification |
|---|---|
| Operating system | Linux / macOS / Windows with WSL2 |
| Container runtime | Docker Desktop with Compose v2 |
| Backend | Python 3.11-slim container, port 8000 |
| Database | `pgvector/pgvector:pg15`, port 5432, named volume |
| Search | `searxng/searxng:latest`, port 8080 |
| Frontend | Vite dev server, Node 18+, port 5173 |
| LLM | Groq API, `llama-3.1-8b-instant` |
| Embeddings | `all-MiniLM-L6-v2`, executed locally on CPU |

Three containers, orchestrated by a single `docker-compose.yaml`. The frontend
runs on the host rather than in a container so hot module replacement stays
responsive.

### 4.1.2 Production

| Component | Specification |
|---|---|
| Backend | Render web service, Docker runtime, free plan |
| Database | Render PostgreSQL 15, free plan, pgvector enabled |
| Frontend | Vercel static hosting with CDN |
| Configuration | Declarative — `render.yaml`, `frontend/vercel.json` |
| Transport | HTTPS throughout, certificates managed by the platforms |
| Secrets | Platform-managed; `JWT_SECRET` generated by Render, never committed |

### 4.1.3 Runtime requirements

| Resource | Development | Production |
|---|---|---|
| Backend image | ~2 GB (includes PyTorch) | ~400 MB (slim set) |
| Memory | ~1.5 GB across containers | Within the 512 MB free tier |
| Database | Local volume | Free plan, 1 GB |
| Cold start | None | 30–60 s after idling |

## 4.2 Local Deployment

Four steps from a clean clone.

**1. Clone and configure**

```bash
git clone https://github.com/its-wasp/personal-adaptive-tutor.git
cd personal-adaptive-tutor
cp .env.example .env
```

Set `GROQ_API_KEY` and `JWT_SECRET` in `.env`. Every other default works.

**2. Start the backend stack**

```bash
docker compose up
```

The entrypoint performs the database preparation automatically, printing
`[entrypoint]` lines as it goes:

1. polls PostgreSQL for up to 60 seconds — Compose's `depends_on` waits for the
   container to exist, not for the database to accept connections;
2. runs `alembic upgrade head`, creating the `vector` extension and all 13
   tables;
3. seeds the 25-concept knowledge graph.

Both steps are idempotent, so subsequent starts skip them. This automation was
added during hardening: previously the steps were undocumented, and a fresh
clone produced a running API over an empty database with a blank dashboard —
defect D7 in section 3.3.3.

**3. Start the frontend**

```bash
cd frontend
npm install
npm run dev
```

**4. Verify**

```bash
curl http://localhost:8000/health        # {"status":"ok"}
curl http://localhost:8000/health/db     # {"status":"ok","database":"connected"}
python backend/scripts/smoke_test.py     # full end-to-end suite
```

Open <http://localhost:5173>.

**Optional — seed reference content for RAG.** The tutor works without it, but
grounding improves noticeably:

```bash
docker compose exec backend python -m app.rag.content_seeder
```

Roughly ten minutes for all 25 concepts; it paces itself to stay inside Groq's
free-tier rate limit.

## 4.3 Cloud Deployment

### 4.3.1 Ordering constraint

The two halves reference each other: the frontend build needs the API's URL,
and the API's CORS allowlist needs the frontend's origin. Neither exists
initially, so deployment must proceed in three stages.

```
   1. Render          2. Vercel                3. Render
   deploy backend  →  deploy frontend with  →  set CORS_ORIGINS to
   obtain API URL     VITE_API_URL set          the Vercel origin,
                      obtain site URL           redeploy
```

Omitting stage 3 yields a site that loads correctly and then fails every
request at the CORS preflight — a failure that presents as a broken frontend
while the backend is entirely healthy.

### 4.3.2 Backend and database

Render reads `render.yaml` as a Blueprint and provisions both the web service
and the PostgreSQL instance. `DATABASE_URL` is wired from the database resource
automatically and `JWT_SECRET` is generated by the platform. Two values are
marked `sync: false` so Render prompts rather than reading them from the
repository: `GROQ_API_KEY`, a secret, and `CORS_ORIGINS`, unknown until stage 2.

`healthCheckPath` is `/health`, which needs no database. A failed migration
therefore surfaces as an unhealthy deploy rather than a service that starts and
then errors on every real request.

### 4.3.3 Frontend

Imported into Vercel with **Root Directory** set to `frontend`, which is
required for `frontend/vercel.json` to apply. `VITE_API_URL` is set to the
Render service URL.

The configuration's substantive element is the SPA rewrite. React Router owns
`/chat/:sessionId`, `/review` and `/profile` entirely client-side, so a hard
refresh or a shared link requests a path with no file behind it. The rewrite
directs everything that is not a built asset to `index.html`. Excluding
`/assets/` rather than rewriting unconditionally means a genuinely missing
bundle still returns 404 instead of HTML served with a JavaScript content type.

### 4.3.4 Configuration reference

| Variable | Required | Scope | Notes |
|---|---|---|---|
| `GROQ_API_KEY` | Yes | Backend | Chat and quiz generation fail without it |
| `JWT_SECRET` | Yes | Backend | Generated by Render |
| `DATABASE_URL` | Cloud | Backend | Takes precedence over `POSTGRES_*` |
| `POSTGRES_*` | Local | Backend | Compose defaults suffice |
| `CORS_ORIGINS` | Cloud | Backend | Comma-separated; localhost always allowed |
| `AUTO_MIGRATE` | No | Entrypoint | Default `1`; `0` skips migrate and seed |
| `GROQ_MODEL` | No | Backend | Default `llama-3.1-8b-instant` |
| `SEARXNG_URL` | No | Backend | Empty disables `/references` |
| `VITE_API_URL` | Yes | Frontend | Build-time; changing it requires redeploy |

## 4.4 Differences Between Environments

Three differences are deliberate and are recorded here rather than discovered
later.

**RAG grounding is unavailable in production.** The deployed image installs
`requirements-prod.txt`, which omits `sentence-transformers`. With PyTorch the
image exceeds 2 GB, beyond the free tier's limit. The embedder detects the
missing import, `is_available()` returns false, the retriever returns an empty
list, and the prompt builder omits the reference block. The tutor continues to
personalise from the learner profile, mastery data and conversation history.
Nothing errors, and no other feature is affected. The dependency set is
selected by a Docker build argument, so restoring RAG on paid hosting is a
one-flag change.

**SearXNG is not deployed.** Running a meta-search engine alongside a free-tier
web service is not viable. `/references` is the only affected endpoint and no
screen currently calls it.

**Free-tier cold starts.** Render idles an inactive free service, so the first
request after a quiet period takes 30–60 seconds. Subsequent requests are
normal. Worth warming `/health` a minute before any live demonstration.

## 4.5 Deployment Verification

Performed after each deployment:

- [ ] `GET /health` returns `{"status":"ok"}`
- [ ] `GET /health/db` reports `connected`
- [ ] `/docs` lists all 24 endpoints with response schemas
- [ ] Sign-up succeeds and returns a token
- [ ] Placement quiz submits and assigns a level
- [ ] Dashboard renders 25 concepts across 5 tiers
- [ ] A session generates an opening explanation
- [ ] A quiz generates, grades, and moves the mastery bar
- [ ] Hard refresh on `/chat/<id>` loads correctly
- [ ] Browser console reports no CORS errors
